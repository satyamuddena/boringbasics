# The admin phone app and push notifications

`/admin` installs to a phone's home screen as an app and pushes a notification when a
booking is **paid** or **confirmed**. It is the same Next.js app, not a separate build —
deploy once and the phone has the change on the next open.

Implementation:

```text
public/admin.webmanifest              app name, icon, start_url, scope
public/sw.js                          service worker (push only — caches nothing)
public/icons/                         generated by scripts/generate-icons.ts
src/app/admin/layout.tsx              links the manifest, iOS meta tags
src/lib/push.ts                       server-only transport, prune, never throws
src/lib/pushTemplate.ts               what the notification says (redaction lives here)
src/components/admin/PushToggle.tsx   the on/off UI, including the iOS instructions
src/app/api/booking/booked/route.ts   trigger: booking confirmed
src/app/api/payment/verify/route.ts   trigger: payment received
```

## One-time setup

Generate a VAPID key pair — **one per environment**, and keep it stable. Rotating the keys
invalidates every device already subscribed, and they will not re-subscribe on their own.

```bash
npx web-push generate-vapid-keys
```

Set four variables (see `.env.example`). `VAPID_PRIVATE_KEY` is a real secret — it
authenticates you to Google's and Apple's push services. It belongs in the Coolify
environment, never in the repo.

```text
VAPID_PUBLIC_KEY=              from the command above
VAPID_PRIVATE_KEY=             from the command above — secret
NEXT_PUBLIC_VAPID_PUBLIC_KEY=  same value as VAPID_PUBLIC_KEY
VAPID_SUBJECT=mailto:you@example.com
```

Until they are set, push is a **silent no-op** — same graceful degradation as an
unconfigured Twilio or Razorpay. Nothing else breaks.

**HTTPS is mandatory.** Service workers and push do not run over plain HTTP. `localhost` is
exempt, which is why local development works.

## Installing it on a phone

**Android (Chrome)** — open the site, Chrome offers "Install app". Accept, then open
`/admin/leads` from the new icon and press **Turn on** in the notifications box.

**iPhone (iOS 16.4 or newer)** — Safari only delivers push to an app on the Home Screen,
never from a browser tab, and there is no install prompt to trigger:

1. Open the site in **Safari** (not Chrome — it must be Safari to install).
2. Tap **Share**, then **Add to Home Screen**.
3. Open Boring Basics from the **new icon**.
4. On Bookings, press **Turn on** in the notifications box.

Until step 3 the toggle deliberately shows these instructions instead of a button, because
a button there would silently do nothing. Deleting the Home Screen icon also deletes the
subscription — re-adding it means turning notifications on again.

Press **Send test** to prove the whole chain works before relying on it.

## What a notification says

Notifications render on a **locked** phone, before any password. They are therefore limited
to a first name and a time:

```text
New booking          Priya · 12 August, 6:00 PM
Payment received     Priya · no slot picked yet
```

No surname, no phone number, no email, no amount, no payment or order id. That rule lives in
`src/lib/pushTemplate.ts` and is enforced by `tests/pushTemplate.test.ts`, which passes a
full booking in and asserts none of it comes out. Add new notification types **through those
builders**, not by hand-writing a payload.

The payload is encrypted end-to-end (`aes128gcm`), so Google's and Apple's relay servers
carry it but cannot read it.

## Staying signed in

The phone stays signed in on a **sliding 30-day window**: every time the app is opened the
clock resets, so weekly use never hits a login screen. A **180-day hard cap** from login
forces a fresh password eventually no matter how active the device is, so a lost phone
cannot stay signed in forever. The rules are in `src/lib/sessionCore.ts` and tested in
`tests/sessionCore.test.ts`.

**An expired session does not stop notifications.** Push subscriptions are keyed to the user
and the browser, never to session validity — otherwise the trainer would silently stop
hearing about bookings a month after last opening the app. A notification tapped after the
session went cold lands on the login page and, once the password is entered, continues to
the booking it was about.

Only four things remove a subscription:

- the trainer presses **Turn off**
- the trainer **signs out** on that device (a deliberate act, unlike an expiry)
- an admin **revokes the device** from Settings
- the push service reports the endpoint is gone (404/410), which prunes it automatically

## Losing a phone

`/admin/settings` → **Signed-in devices** lists every browser signed in as you, with the
device, IP, when it signed in and when it was last used. **Sign out** ends that session and
deletes its push subscription in the same action, so it stops showing client names on a lock
screen you no longer control. Recorded in the audit log as `session_revoked`.

## When a notification does not arrive

1. **Check the audit log** — `/admin/audit`, action `push_notify`. Every send is recorded
   with how many devices it reached, failed or pruned.
2. `sent: 0, skipped: "Push is not configured"` — the VAPID variables are missing from the
   environment.
3. `sent: 0, skipped: "No devices have notifications turned on"` — nobody has pressed
   **Turn on**, or the subscription was pruned.
4. `pruned: 1` — that device's subscription was dead and has been forgotten. Press **Turn
   on** again on the phone.
5. **iPhone showing instructions instead of a button** — the app is being opened from a
   Safari tab, not the Home Screen icon.
6. **Nothing at all, no audit row** — the trigger did not fire. Check the booking actually
   reached `paid`/`booked`; the audit log records those separately.

## Keeping it in sync with future changes

The phone runs the same code as the laptop, so a deploy is all that is needed. Four things
keep that true, and they are deliberate:

1. **`public/sw.js` caches nothing.** A caching service worker is the only way a PWA goes
   stale, and stale bookings are the problem this app exists to solve. The `fetch` handler
   is a pass-through that exists purely because Chrome requires one before offering to
   install the app.
2. **The worker updates immediately** — `skipWaiting()` + `clients.claim()`, and `/sw.js` is
   served `no-cache` from `next.config.ts`. Without that header a browser may reuse a worker
   from a previous deploy for up to 24 hours.
3. **`scope: "/admin"`** means every future admin page is inside the app automatically, with
   nothing to register per page.
4. **The worker is payload-driven.** It renders whatever `title`, `body`, `url` and `tag` the
   server sends. A new notification type is one `sendAdminPush(...)` call on the server —
   no worker change, and nobody has to reinstall.

**The one exception:** the app name, icon and `start_url` are read by the OS at install time
and cached there. Changing them needs a remove-and-re-add on each phone. Regenerate icons
with `npx tsx scripts/generate-icons.ts` after changing the brand mark, and commit the PNGs.
